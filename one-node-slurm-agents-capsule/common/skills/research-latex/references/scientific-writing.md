# Scientific report quality and evidence handling

## Input audit

Before drafting, enumerate relevant inputs: tables, raw files, checkpoint paths, plotting scripts, notes, DOI links, conference papers, metrics. Identify missing information. Do not infer measurements from filenames or visually estimate exact values from figures where numerical data exist.

For ML/chemical language model reports, record (when available):
- Task definition, endpoints, train/validation/test separation, leakage prevention, data cleaning and de-duplication.
- Molecular representation (SMILES canonicalization/randomization, stereochemical handling, tokenization, max length, vocabulary size); source/version/quality restrictions.
- Architecture, parameter count, initialization, seeds, optimizer, scheduler, precision, hardware allocation, step/epoch/token counts, checkpoints, software versions and Git commit.
- Primary and secondary metrics, sample count, uncertainty intervals, class balance, statistical tests and exclusions. For model comparisons, match data splits and evaluation protocols.
- In learning-dynamics analysis, distinguish *empirical phase transition / rapid metric change* from mechanistic interpretation; a probe or CKA change is evidence about a measurement, not automatic proof of causal representation reorganization.

## Recommended structures

### Academic (`academic`)

Title + authors + abstract → background and contribution → methods → experimental setup → results → discussion and limitations → conclusion → references. Supplementary appendices when appropriate.

### Technical (`technical`)

Executive summary/abstract → question → inputs/provenance → experimental settings → results (plots/tables) → interpretation → limitations → next actions → references → appendix. This is the default for frequent experiment reporting.

### Monograph (`monograph`)

Title page → preface → TOC → prerequisites → foundational concepts/definitions → derivations/propositions → methods/taxonomy → applications → limitations and open questions → references. Keep chapters modular and cross-referenced.

## Evidence contract

1. Every quantitative claim traces to a source file and computation, or is clearly labeled an estimate/assumption. Every number in the prose must belong to one of the provenance types below.
2. Never present demonstration content as a measurement or cite illustrative bibliography automatically.
3. Verbatim quotations are short and attributed; paraphrases should remain faithful.
4. Never invent DOI identifiers, author order, titles or results. Verify against papers/citable metadata where possible.
5. Distinguish **observed**, **hypothesized**, **planned** and **unavailable**.
6. Use units, dimensions, significant figures and confidence estimates appropriately.
7. State exclusions, negative results, failure modes, caveats and possible alternative explanations.
8. Keep date/time and experimental versioning explicit; do not fill placeholders silently.
9. Treat all generated figures as part of the scientific record; keep generation commands/scripts and source datasets.
10. Prevent accidental disclosure of private research datasets, credentials, or unpublished results when publishing or archiving.

## Number provenance

Tables and figures generated by a script from the primary data tend to stay right. Numbers typed into sentences go wrong: they are copied from a design note, a docstring, a previous draft or a constant in a plotting script, and those copies are not updated when the data change. In one 179-page report, 37 of about 1,100 numbers were wrong, and none of them were in the generated tables. Every number in the prose has one of three origins, and each origin has its own check.

| Type | Origin | How it is checked | Typical document |
|---|---|---|---|
| A | Machine-readable data you hold | Recomputed by `scripts/verify_claims.py`; `verify` fails when the text no longer matches | technical |
| B | Another author's paper or published data | Cite with the location inside the source: `\cite[Table 3]{smith2024}`, `\cite[p.~12]{key}`, `\cite[Eq.~4]{key}` | academic, monograph |
| C | A definition or derivation in this document | Put the derivation in the text; check symbolic steps by computation where possible | monograph |

A type-A check returns the exact text the `.tex` must contain (number, unit, rounding and the surrounding words), not only the number, so a changed unit or rounding also fails. For a type-B number, the machine can only check that a location is declared; a person still checks that it is right. `verify` lists sentences with numbers but no `\cite`, `\ref` or `\label`, and citations without a location. In-text arithmetic and counts such as "three types" will appear in that list too; the list does not have to be empty, but every number in it must be accounted for.

## How quantitative claims go wrong

These are observed failure modes, not hypotheticals. Each one survived several proofreading passes of a 179-page report because none of them is visible without going back to the source. The examples come from one chemistry/ML report and are there to make each mode concrete; the modes themselves are not domain-specific. Modes 1-5, 7 and 9 need data of your own; modes 6, 8 and 10 apply equally to a survey or a textbook that only cites other people's numbers.

1. **Prose copied from a secondary source.** Tables are generated from data; prose is typed from a design doc, a docstring, a previous draft, or a constant inside a plotting script. The table is right and the sentence next to it is wrong. Treat any number that is not produced by the same path as the tables as unverified.
2. **Arithmetic on displayed values.** A difference computed from two rounded figures (0.6674 − 0.2665 = 0.4009) disagrees with the same difference computed from the originals (0.4010). Compute from the originals, then round once.
3. **Scope slippage.** A count that covers one arm is written as if it covered the whole population (7,568 of one group presented as the total, which is 7,916). State the denominator in the sentence.
4. **Mixed settings inside one comparison.** A before/after pair drawn from two different evaluation settings (one from the averaged weights, one from the raw weights) reads as a single controlled comparison. Name the setting that is held fixed.
5. **Mixed metrics inside one sentence.** A hit rate and a yield reported in the same clause, with only the second one named.
6. **Identity errors in lookups by display name.** Resolve entities by stable identifier, never by the name a database happens to show. Display names get renamed, differ between records of the same kind, and collide across namespaces, and a name-based query that misses returns a plausible wrong row rather than an error. Illustration: one HDAC isoform is stored under a `Protein deacetylase ...` name while its siblings use `Histone deacetylase ...`, so a prefix search for the latter silently substituted a different species' ortholog and lost 9 of 12 relevant compounds. The same shape appears with gene symbols, author names, ticker symbols and product codes.
7. **A correction applied in one place only.** The body is fixed and the abstract keeps the old figure. Run `crosscheck` after every round of corrections (step 8 of `SKILL.md`).
8. **Self-contradiction across adjacent sentences.** "These are excluded from the stratified analysis" followed by "these are included in the stratified analysis." Neither the compiler nor a structural validator sees it. Read each claim against the one before it.
9. **Double counting in an aggregate.** A total described as "the three runs" that in fact sums four.
10. **An unreproducible survey.** A number quoted from a query that was run once and never saved. Save the query as a script and its output as a file in the project, then cite the file.

## Independent checks

Independent reviewers are not independent if they share a method. Two agents asked the same question of the same database, both resolved the target by display name, and both returned the same wrong count. Adding a third would have returned it again. For numeric claims, prefer one re-derivation that goes through a different access path over several reviewers that go through the same one. Image-capable reviewers remain the right tool for the visual page check.

## Verification before delivery

- Are the title, authorship, affiliations and date accurate?
- Do figures/tables come from real data, and are transformations auditable?
- Do axis labels define units and normalizations?
- Does each caption describe sample count, relevant experimental context and the meaning of uncertainty?
- Do plots/claims match the inputs (including baselines and versions)?
- Are citations relevant and genuinely verified?
- Are results and interpretations separated and limitations stated?
- Is enough methodology preserved for a peer to reproduce the measurements?
- Does every number in the prose come from the same path as the numbers in the tables?
- Does `scripts/verify_claims.py` cover every load-bearing number, and does `verify --all` pass?
- Does the abstract (and any conclusion or limitations section) still agree with the body after the latest round of corrections (`crosscheck`)?
