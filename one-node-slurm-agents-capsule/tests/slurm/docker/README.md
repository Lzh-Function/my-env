# Dockerによる疑似クラスタの結合テスト

Docker 内に投入元の `controller` と計算ノードの `compute` を作り、**実際の Slurm と Apptainer で、このリポジトリの `agentrun` を実行**します。参照元は `agent-capsule` の疑似クラスタテストです。エージェントは Claude Code と Codex の二つに限定し、この環境の認証・出力要件・履歴保存・相互監査に合わせています。

エージェントの CLI、インストーラの配布先、GitHub API の応答には固定のテストデータを使います。実際のアカウントへのログインやモデルの呼び出しは行いません。

## 実行方法

カプセルのルート（`install.sh` があるディレクトリ）から実行します。

```bash
tests/slurm/docker/run.sh
```

次の処理を順番に実行します。

1. テスト用 Docker イメージをビルドする。
2. MUNGE、Slurm コントローラ、計算ノードを起動する。
3. Slurm の割り当てを取得し、一般ユーザーとして Apptainer を実際に起動して前提条件を確認する。
4. 主要機能の結合テストを実行する。
5. Ubuntu の投入元コンテナで、既存の Python 回帰テストを全件実行する。MCP SDK を導入した Python を使うため、MCP 通信のテストも実行する。
6. ログと成果物を回収し、今回作成したコンテナ・ネットワーク・ボリュームを削除する。

テスト名を指定して実行することもできます。指定した結合テストの後に、既存の回帰テストも実行します。

```bash
tests/slurm/docker/run.sh ClusterTests.test_cross_review_both_providers_cli_mcp_and_central_archive
```

GitHub Actions の `.github/workflows/slurm-capsule-tests.yml` からも同じスクリプトを実行します。ビルド・起動・テストの失敗は、そのまま検査の失敗として扱います。Slurm や Apptainer が起動できなかった場合に、疑似実装へ切り替えて通過させることはありません。

## 必要な環境

- x86-64 の Linux Docker エンジンと Docker Compose。
- cgroup v2 と、コンテナ専用の書き込み可能な cgroup 階層。
- 特権コンテナと、一般ユーザーによるユーザー名前空間の作成を許可する環境。
- イメージのビルド時に Ubuntu のパッケージ配布先、GitHub、Python パッケージの配布先へ接続できること。

計算ノードのコンテナは、入れ子の Apptainer と Slurm の cgroup 管理のために `privileged: true` を使います。Docker ソケットやホストのディレクトリ、本番の Slurm 設定・認証情報はマウントしません。ポートも公開しません。

AppArmor などが一般ユーザーの名前空間を制限するホストでは、特権コンテナでも Apptainer が起動できない場合があります。起動確認が失敗した場合は、[Apptainer の公式導入手順](https://apptainer.org/docs/admin/latest/installation.html#running-inside-docker)とホストの設定を確認してください。`run.sh` はホストの sysctl を変更しません。GitHub Actions では、使い捨ての実行用 VM に限って名前空間の制限を一時的に調整し、終了時に元に戻します。

## クラスタの構成

| 項目 | 構成 |
| --- | --- |
| OS | Ubuntu 24.04 |
| Slurm | `23.11.4-1.2ubuntu5` のパッケージに固定 |
| Apptainer | 1.5.3。配布パッケージの SHA-256 を検証 |
| 認証 | 今回のテスト専用に生成した MUNGE キー |
| プロセス・資源管理 | `proctrack/cgroup`、`task/cgroup`、`select/cons_tres`、`CR_Core_Memory` |
| 投入元 | Apptainer とエージェント CLI を `PATH` に置かない |
| 計算ノード | 同じ UID の別ユーザー名を使用。投入元のホームは存在しない |
| 共有領域 | テスト専用の名前付きボリューム `/shared` |
| ノード固有領域 | 計算ノードだけに `/scratch/capsule` を用意。コンテナからは `/node-scratch` |
| 通信 | 実行中のネットワークは内部専用。外部のモデル API に接続しない |
| MCP | 実際の `uv` と `mcp==1.26.0` を使用。依存パッケージはビルド時に取得して実行ごとのキャッシュへ用意 |

Slurm の `KillWait=30` などは参照元と同じ設定です。1 分のタイムアウト試験では、実際のスケジューラが時間制限を適用します。Python の待ち時間を短縮して代用することはありません。ジョブ投入待ちの短縮のため、テストクラスタのスケジューラ起動間隔だけを調整しています。

計算ノードは CPU 4 コア、メモリ 64 GiB を Slurm に申告します。これは割り当て判断用の情報で、Docker に 64 GiB を確保する指定ではありません。通常のテストジョブは CPU 1 コア、メモリ 512 MiB を要求します。

## 検証する機能

| 機能 | 結合テストで確認する内容 |
| --- | --- |
| エージェントと実行モード | Claude Code / Codex と、`assist` / `experiment` / `campaign` / `review` / `multi-review` の全 10 組み合わせ。起動、資源指定、実際の CPU 割り当て、設定、成果物、終了状態を確認 |
| 対話起動と再開 | 実際の `srun --pty`、端末設定の復元、一時ホームの削除、履歴のプレビュー、同じ会話 ID での再開、追加マウント・資源・秘密情報の参照先・実行中に変更した設定の継承、確認を断った場合の中止 |
| 時間制限 | 両エージェントで本物の Slurm タイムアウトを起こし、端末・ロックの解放後に再開 |
| 失敗からの復旧 | エージェントの異常終了、配布先の名前解決失敗、インストーラの失敗。終了コードの記録、一時ホームの削除、再実行を確認 |
| 排他と中止 | 実行中のリポジトリでの重複起動の拒否、`scancel`、投入元プロセスへの SIGTERM、停止した終了処理からの回復 |
| 認証 | 固定のテスト用 CLI によるログイン、認証ストアへの取り込み、リセット、計算ノードへの一時配置 |
| マウント | 空白・引用符を含むパス、読み取り専用・書き込み可能な追加マウント、共通フック・スキルの読み取り専用保護、Claude の設定ファイルを一時ファイルから置き換えて保存できること |
| ノード固有 SSD | 投入元から見えない `/scratch/<投入元ユーザー名>` の公開、既存 `/scratch` との分離、不在時の起動継続と非作成 |
| フックと状態表示 | 実際にマウントされたフックによる禁止コマンドの拒否、コマンド記録、Claude の状態表示スクリプト |
| 秘密情報と GitHub | 環境変数の受け渡し、環境記録への非掲載、実際の別コンテナとソケットによる GitHub 操作の仲介、トークンの秘匿、許可外のコマンド・リポジトリの拒否 |
| 会話履歴 | 投入元での自動回収、Markdown へのコマンド出力の収録、SQLite、投入場所の記録、再保存 |
| 相互監査 | 両方向で CLI と MCP を使用。質問への回答、同じ会話の継続、修正後の第 2 ラウンド、上限超過の拒否、監査履歴の集約 |
| 監査の失敗 | 相手の認証不足と監査の時間切れを記録し、作業エージェントは実行を続けられること |
| ウィザード | 端末で入力し、実際の Slurm ジョブとして会話を再開 |
| 管理コマンド | 設定検証、環境診断、実行計画、目標ファイル生成、状態・ログ・一覧・保存先・成果物確認、基本動作テスト |
| スキル管理 | 取り込み、既存スキルの維持、強制上書き、Claude / Codex の設定同期 |

各テストは、生成されたコマンド文字列だけでなく、実行中のコンテナ内の状態や終了後のファイルを確認します。既存の回帰テストでは、UI 別の戻る・中止、補完、同じ秒での実行 ID 競合、設定生成、履歴解析、監査状態の回復なども確認します。

## ログと後片付け

実行ごとに固有の Compose プロジェクト名を使います。ログは既定で `.agent-runs/one-node-slurm-*/` に残ります。

| 保存先 | 内容 |
| --- | --- |
| `build.log` / `startup.log` | イメージのビルドとクラスタの起動記録 |
| `tests.log` | 結合テストの結果 |
| `unit-tests.log` | 既存の Python 回帰テストの結果 |
| `cluster.log` | Slurm・MUNGE・Apptainer などのコンテナログ |
| `work/` | 各テストの作業リポジトリと実行記録 |
| `history/` | 共通の Markdown・SQLite 保存領域 |

`SLURM_TEST_ARTIFACTS` で保存先を変更できます。GitHub Actions ではログと成果物を `slurm-capsule-test-logs.tar.gz` にまとめ、7 日間保存します。引用符などを含む検証用のファイル名も保持するため、ダウンロードした成果物に含まれる tar.gz を展開して確認してください。

正常終了・失敗のどちらでも、今回のコンテナ、ネットワーク、名前付きボリューム、自動命名したイメージを削除します。Docker のビルドキャッシュや他のプロジェクトの資源は削除しません。`SLURM_TEST_IMAGE_TAG` を明示した場合は、そのイメージを残します。

端末や Docker が強制終了して後片付けが走らなかった場合は、出力されたプロジェクト名で削除してください。

```bash
docker compose -p PROJECT_NAME -f tests/slurm/docker/compose.yaml down --volumes
```

## 確認できない範囲

このテストは、実際のスケジューラ、コンテナ起動、マウント、プロセス管理、履歴保存を確認するものです。実際のモデル応答、上流 CLI の変更、配布先の現時点の応答、実アカウントの認証は別途確認が必要です。

結合テストには、起動に必要な基盤プログラムと固定のエージェントを含む専用 SIF を使います。本番の `base-system.def` 全体のビルド、Rust・TeX の実行、GPU、NFS・autofs の障害、サイト固有の prolog / epilog / PAM、systemd の設定までは再現しません。共有ボリュームはローカルファイルシステムです。コンテナはホストと同じカーネルを使うため、Ubuntu イメージを変えてもカーネルの差は検証できません。

実クラスタ用の検査は [上位のテスト手順](../README.md)を参照してください。
